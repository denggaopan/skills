# fast-do - 快速端到端执行任务

把明确的开发任务连续推进到可验证的结果，完成用户已授权的收尾动作，尽量少打断用户。Claude Code 与 Codex 共用这份流程，不依赖特定插件。

客户端应用的开发与修复任务，默认把打包和发布纳入交付目标，沿用项目既有的发布渠道和流程；用户明确要求只改代码、不发布，或仅修改文档等不影响客户端交付的内容时，按该范围执行。

开始时简短说明：`使用 fast-do：检查工作区，按复杂度执行，验证后完成约定的收尾。`

## 平台适配

- 以当前会话实际暴露的工具、权限和运行模式为准。工具名相似不代表参数兼容；不要调用不存在的工具或绕过 Plan mode、沙箱和审批限制。
- Claude Code 用 `/fast-do <任务>`；Codex 用 `$fast-do <任务>`。从调用消息与对话中读取任务，不依赖 Claude 专属的参数占位符、命令注入或子代理 frontmatter 扩展。
- 遵循当前平台加载且适用于目标文件的仓库指令，例如 `CLAUDE.md` 或 `AGENTS.md`；其中的项目验证、分支和提交约定优先于本技能的通用默认值。
- 需要选择平台工具、安装位置或手动创建 worktree 时，读取 [references/platforms.md](references/platforms.md)。常规任务不必加载整份参考。
- `superpowers`、项目的运行或提交技能都是可选增强：仅在已安装且适用时使用。不先安装插件，也不因缺少它们停止；直接按下面的流程完成同等工作。

## 1. 确认任务与工作区

先确定交付目标、验收方式和收尾范围，从代码与现有约定推断常规实现选择。用户只要求计划或评审时，遵守该范围；用户要求修复 bug 时，先定位和复现，再实现修复。

涉及客户端交付时，先从项目脚本、CI 和发布文档确定目标系统与架构、版本规则、打包命令、签名要求及发布渠道。提前识别推送分支或 tag 是否会触发自动发布，按实际依赖安排步骤；已有流程和授权能确定的事项不重复询问。

在 Git 仓库中检查当前分支、工作区状态、已有 worktree，以及相关仓库指令。记录任务起点和已有修改。目标分支与远端按用户要求、项目约定和仓库信息确定，不写死 `main` 或 `origin`。

**隔离选择：**

- 已在为本任务准备的 worktree、独立 checkout 或用户指定分支中，直接复用，不嵌套创建。
- 改动范围较大、需要并行写入或应避免影响当前 checkout 时，优先新建 worktree；小范围且容易验证的改动可直接在当前工作区完成。
- 新 worktree 只包含所选提交的内容，不会自动带上未提交或未跟踪文件。任务依赖这些文件时，优先在现有工作区继续；确需隔离时，先明确如何携带本次任务所需内容。
- 保留用户已有修改。不要为隔离、切分支或比较测试基线而自动 stash、清理或重置工作区。
- 无 Git 仓库时直接执行文件任务；无法创建 worktree 时，在当前环境可安全完成就继续并说明。不要为套用流程自行初始化仓库。

## 2. 按复杂度选择执行方式

| 情况 | 执行方式 |
|---|---|
| 改动集中、逻辑明确、局部验证即可 | Inline：当前会话直接做 |
| 探索量大或跨模块，能拆出边界清楚的独立任务，且允许委派并有可用工具 | Subagent：分派独立任务，主代理整合 |
| 任务复杂但子任务强依赖、没有子代理工具或当前规则不允许委派 | 分阶段 Inline：列出简短计划，逐步实现与验证 |

复杂度决定拆解粒度，不意味着必须调用子代理。简单任务不增加编排开销；只有可独立推进的工作才并行。

## 3. 执行并保持推进

**直接执行：** 先选与改动匹配的验证方式，再完成最小必要实现。修复逻辑错误或新增行为时，适合则补充能暴露问题的回归测试；文档、注释或低影响的机械修改不强制测试驱动开发。

**子代理协作（可用且允许时）：**

- 每个任务给出目标、所需上下文、准确工作目录、可修改文件范围和验收标准。独立任务可并行，互相依赖的任务按顺序执行。
- 不默认子代理会继承当前 worktree。明确其工作目录；共享工作区时避免并发修改同一文件，使用独立 worktree 时由主代理统一集成改动。
- 主代理继续推进不依赖子任务结果的工作，接收结果后检查实际差异、整合并验证。子代理报告不能替代最终验证。
- 审查结论按复现、代码路径和测试证据判断，不按代理投票数判断。工具不可用或额度用尽时，接回当前会话继续。

**遇阻处理：**

- 可逆的实现选择和非关键歧义，采用最符合仓库约定的默认值继续；只说明会影响结果的假设。
- 工具失败时先依据错误调整方法；同一原因反复失败就换路径或报告具体阻塞，不无限重试。
- 只有缺失的信息会实质改变结果，或下一步确需新增授权且无法从会话推断时，提出最少的问题；期间继续不依赖回答的工作。已有授权持续有效，不重复确认。
- 按当前平台可用的交互方式询问；无专用询问工具时用简短文字。非交互环境不等待无法获得的回答，先完成可执行部分并明确剩余阻塞。

## 4. 验证结果

先检查项目实际的验证入口，例如仓库指令、`package.json`、Makefile 或 CI 配置，再运行相关检查。

- 优先运行受影响的测试、类型检查或 lint；只有项目要求或改动范围需要时才扩大到全量回归。
- 有运行时行为变化时，尽可能实际走通受影响流程，例如启动服务、调用接口或操作页面。构建通过不能替代对行为的验证。
- 客户端还要验证实际交付包的安装或解压、启动及受影响的关键流程；涉及升级时检查升级路径。开发模式运行正常不能代替打包产物验收，具体打包与发布见第 5 节。
- 仅修改文档或配置时，检查格式、引用和可用的配置校验器；不为纯文档改动启动无关服务。
- 区分已有失败和本次引入的问题。需要基线对比时，用已记录的结果或独立的临时 checkout，保留当前工作区。
- 无法运行某项验证时，说明具体原因和已完成的替代检查；未运行、失败、通过要明确区分。拿到证据后才声称对应项通过。

验证后检查最终差异，确认只包含本次任务范围内的改动。

## 5. 完成约定的收尾

根据用户本次与此前的授权连续推进。已要求“提交、合并并推送”就执行完整流程；客户端开发任务还需按约定完成打包与发布。用户明确限制为只改文件或不发布时遵守该限制，不扩展到未经约定的发布渠道或部署目标。

按项目版本策略准备发布；需要手工更新的版本号、构建号和发布说明，在对应提交或发布触发动作之前完成，自动管理的版本则交给既有流水线。若发布由 CI 触发，先满足该流程的检查与发布条件，再推送对应分支或 tag。

1. **提交（已授权时）：** 检查 diff 和暂存区，只暂存和提交本次相关差异。已有无关的暂存内容时，保持其原有状态，不能一并提交；同一文件混有用户改动时按差异块区分。遵循项目提交规范，不混入无关版本号变更。
2. **集成（已授权时）：** 确认目标分支、远端与工作区状态；需要远端信息时先 fetch。遵循项目的直接合并或 PR 流程，受保护分支走 PR，不强推绕过保护。
3. **处理分支关系：** 只有分支关系允许时才能快进。分叉时按项目约定合并或变基，处理与本任务有关的冲突后重新运行受影响检查；不为追求快进而重置分支或改写他人的历史。原 checkout 有未提交修改时，不在那里切分支或做集成。
4. **推送（已授权时）：** 使用明确的远端和目标分支，检查相对远端将新增的全部提交。混有不相关的本地提交时先隔离本次提交，不能一并推送；新远端分支则相对任务基线检查。推送后核对远端分支包含预期提交；被拒绝时按原因处理，不强推兜底。
5. **客户端打包：** 使用项目正式打包入口，覆盖本次约定的系统和架构，按渠道要求完成签名或公证。检查产物是否生成、版本及构建号是否正确，并执行交付包验收。记录产物路径或 CI 下载地址及对应源码版本；验收后源码、版本或打包配置有变化时，重新打包并验证。缺少本机工具链时优先使用既有 CI，缺少必要凭据时保留可验证的产物并报告具体阻塞。
6. **客户端发布：** 将已验证的产物按既有流程发布到约定渠道，例如 Release 附件、应用商店或更新服务；按项目要求同步发布说明和更新元数据。跟进发布任务并核对渠道中的版本、下载入口或分发状态；草稿、上传完成、等待审核与正式可用要分别报告。发布请求超时或失败时先查询渠道状态，避免重复创建版本或覆盖已有产物。代码推送或 CI 启动成功不代表发布完成。
7. **交付状态：** 简洁说明改动、验证结果、关键默认决策，以及实际的提交、PR、合并或推送状态。客户端还需给出版本号、产物位置、包验收结果、发布渠道及发布链接或当前状态。留有 worktree 或未完成步骤时给出位置和原因；打包失败或发布仍受阻、待审核时，明确区分已完成部分与剩余步骤，不声称完整交付。

需要用户做最终决定时，先把已授权的实现和验证做到可审阅状态，再提出具体问题。
